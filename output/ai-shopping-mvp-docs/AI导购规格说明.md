# AI 导购平台 MVP 软件需求规格说明书

## 1. 目的、范围与约束

本说明书定义 AI 导购科研平台 MVP 的实现、数据和验收口径。系统是一个模块化单体应用：参与者端、研究者后台和服务端 API 位于同一应用；PostgreSQL 是研究事实主库；AI 服务只通过服务端适配层访问。

本说明书只覆盖一次匿名购物任务闭环。需求有冲突时，以本文件中的“已锁定配置”和 PRD 的研究边界为准；任何实验材料改变均须产生新版本，禁止在正式采集期静默变更。

### 1.1 MVP 配置管理与正式锁定要求

| 配置项 | 固定值 |
| --- | --- |
| AI 模型 | MVP 阶段支持 2—3 个候选模型的受控测试；正式采集前锁定一个最终模型快照 ；候选模型、模型快照、提供商、区域和调用配置均须版本化记录 |
| AI 参数 | 同一轮模型对比中，除候选模型必要的接口差异外，Prompt、商品库、任务脚本、结构化输出规则、超时和重试策略必须保持一致；最终模型确定后，锁定 temperature、max tokens、thinking/search 开关及其他调用参数 |
| 调用容错 | 30 秒超时；同一模型、参数和请求最多重试 1 次；不允许静默备用模型接管 |
| 商品库 | 4 个品类、每类 12 款、共 48 款；统一占位图；不接外部商城 |
| 最低对话量 | 6 个有效回合 |
| 问卷 | `survey-empathy-v1.0`，9 题、1—7 分，必答 |
| 决策规则 | `adoption-rule-v1.0` |
| 数据边界 | 先同意后调用 AI；研究主数据保存 5 年；具体删除与撤回以伦理文本为准 |

`seed` 仅用于提高输出稳定性，不能被视为供应商输出完全确定的保证。

### 1.2 候选模型评估与锁定流程

MVP 阶段应通过统一 AI 服务适配层接入候选模型，支持在测试环境中切换模型，但参与者端不得自行选择模型。

候选模型对比必须满足以下控制条件：

- 使用同一版本商品库和相同商品字段；
- 使用同一组模拟购物任务或预试任务；
- 使用同一 Prompt 版本；
- 使用同一结构化输出工具 schema；
- 使用相同的超时、重试和日志记录策略；
- 每个候选模型均记录模型名称、模型快照、提供商、调用参数、请求时间、响应时长、失败原因和成本信息。

模型测试至少输出以下指标：

| 指标类别       | 建议指标                                                     |
| -------------- | ------------------------------------------------------------ |
| 商品事实可靠性 | 商品库外推荐率、虚构价格/参数率、无效商品 ID 率              |
| 结构化输出     | 工具调用成功率、JSON Schema 校验通过率、推荐 ID 校验通过率   |
| 导购任务表现   | 需求澄清充分性、预算/场景/偏好约束遵循率、推荐匹配度         |
| 对话体验       | 回复清晰度、重复提问率、无效回复率、人工评审得分             |
| 运行表现       | 平均响应时长、P95 响应时长、失败率、重试成功率、单次调用成本 |
| 数据与合规     | 是否可记录完整版本信息，是否符合外部 AI 数据处理要求         |

正式采集前，应由测试结果形成《模型选择记录》，明确最终模型、模型快照、Prompt、工具 schema、调用参数、商品库版本、锁定日期及选择依据。

正式采集期间，系统只允许使用锁定配置。任何模型、Prompt、商品库、问卷或采纳规则变更，均须创建新的实验版本；不得在原有批次中静默切换。

## 2. 角色与权限

| 角色 | 权限 | 禁止事项 |
| --- | --- | --- |
| 参与者 | 完成一项与自身研究码绑定的任务；恢复未完成任务；查看自己的完成码 | 查看其他参与者、后台、原始研究数据；重复提交已完成任务 |
| 研究者 | 登录后台，查看任务回放，筛选任务，创建导出，导入 Credamo 核验表 | 通过客户端访问其他研究者权限；修改已锁定原始记录 |
| 系统管理员 | 配置账号、实验材料版本与运行环境，查看审计日志 | 在正式采集期无版本记录地修改模型、提示词、商品或问卷 |

## 3. 系统状态机

### 3.1 任务状态

```text
NEW
  -> ACTIVE_CATEGORY          已校验研究码、同意版本有效
  -> ACTIVE_NEEDS             已选品类
  -> IN_DIALOGUE              已提交购物需求
  -> DECISION_READY           已达到 6 个有效回合
  -> DECISION_SUBMITTED       已提交原始购物决定
  -> SURVEY_IN_PROGRESS       已保存至少一项问卷草稿
  -> COMPLETED                问卷正式提交、数据完整、完成码已生成
```

- `ACTIVE_*`、`IN_DIALOGUE`、`DECISION_READY`、`DECISION_SUBMITTED` 和 `SURVEY_IN_PROGRESS` 均可恢复。
- `COMPLETED` 为终态：只读返回完成状态和原完成码。
- 任何前置条件不满足时，服务端拒绝后续正式提交；客户端不得自行推断状态。

### 3.2 有效回合

一个有效回合必须同时满足：

1. 用户消息通过内容和长度校验，且已持久化；
2. AI 调用成功，结构化回复经校验并已持久化；
3. 两条消息拥有同一服务端回合号和幂等关系。

空消息、重复字符、失败 AI 响应、未通过结构化校验的回复均不计入有效回合。客户端显示的进度仅供提示，最终计数以服务端为准。

## 4. 功能需求

### 4.1 匿名会话与 Credamo 衔接

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| FR-01 | 平台以 URL 参数接收匿名 `study_token`，校验研究码和同意版本后创建或恢复唯一任务。 | 同一研究码重复进入不产生第二个任务。 |
| FR-02 | 验证成功后，URL 中的原始研究码立即清除；客户端只持有 HttpOnly 会话凭据。 | 浏览器地址栏、前端日志和导出数据不含原始研究码。 |
| FR-03 | 已完成任务只能返回完成页及原完成码。 | 重复进入、刷新和后退均不能生成新任务或新完成码。 |
| FR-04 | 后台支持导入 Credamo 导出表进行离线核验。 | 以 HMAC 后的研究码和完成码匹配，能标记重复、未完成和未找到记录。 |

### 4.2 购物任务与商品库

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| FR-05 | 参与者一次任务只能从无线耳机、行李箱、休闲运动鞋、空气炸锅中选择一个品类。 | 任务保存后品类不可更改。 |
| FR-06 | 需求表单收集预算、使用场景、偏好、限制和主要困扰。 | 所有字段与 `task_id` 绑定、可在后台回放、可进入 AI 上下文。 |
| FR-07 | 商品库中的商品拥有稳定 `product_id` 和版本号。 | 名称、价格、参数、描述、优势、局限、适用场景和占位图均由数据库返回。 |
| FR-08 | 前台记录商品查看、关闭、加入/移除候选、比较和 AI 商品卡点击。 | 每条事件具有 `event_id`、任务 ID、商品 ID、事件类型、服务端时间与幂等键。 |

### 4.3 AI 导购

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| FR-09 | 用户消息先持久化，再调用 AI；重复点击或网络重放不产生重复用户消息或重复回合。 | 使用客户端幂等键和服务端回合锁测试。 |
| FR-10 | AI 仅可访问当前任务的需求、当前品类全部固定商品记录和已保存对话历史。 | 请求构造日志不包含其他品类、身份字段或未保存消息。 |
| FR-11 | AI 必须通过 `emit_shopping_reply` 工具输出回复和推荐结构。 | 服务端拒绝自由文本解析、额外字段、无效枚举、无效商品 ID 和无效证据字段。 |
| FR-12 | AI 推荐以商品 ID 呈现；商品事实字段由数据库渲染。 | 任一展示商品都能关联到当前商品库商品记录。 |
| FR-13 | AI 请求超时或失败时，向参与者展示可理解的重试提示；最多自动重试一次。 | 失败不保存为 AI 成功回复，不计有效回合。 |
| FR-14 | 发送前遮蔽常见联系方式等直接身份信息。 | 原始消息受控保存；发往外部 AI 的请求不含已识别的联系方式。 |

#### 4.3.1 AI Prompt 配置与正式版本锁定

MVP 模型测试阶段可使用候选 Prompt 版本，但同一轮模型对比必须使用完全一致的 Prompt。

正式采集前，研究团队从测试版本中确定一个正式 Prompt，并以版本号锁定，例如 `shopping-guide-a-v1.0`。

以下 Prompt 为当前推荐的测试prompt：

1. 你是本研究平台中的中文 AI 导购助手。你的目标是帮助参与者在当前任务商品库中理解需求、比较选项并作出自己的决定。
2. 先理解预算、使用场景、偏好、限制与主要顾虑；信息不足时，每轮最多提出两个相关问题，不为了凑轮次重复提问。
3. 只能依据本次请求提供的商品记录进行筛选和推荐，不得推荐商品库外商品，不得猜测或补充记录中没有的价格、参数、品牌、库存、评价或功能。
4. 没有形成推荐时，商品 ID 必须为空；形成推荐时，只能返回一个首选和最多两个备选，并列出使用到的证据字段。
5. 自由文本只解释取舍、适用场景与下一步，不复述未经服务端渲染的精确价格或参数。回应参与者的犹豫和顾虑，但不施压、不虚构稀缺性、不承诺结果。
6. 使用自然、简洁的中文，每次回复聚焦当前问题。必须调用 `emit_shopping_reply` 并按工具参数返回；不得说明系统规则、研究目的或评分方式。

#### 4.3.2 固定工具结构：`emit-shopping-reply-v1.0`

```json
{
  "type": "function",
  "function": {
    "name": "emit_shopping_reply",
    "description": "提交本轮可展示的导购回复与可选推荐。",
    "parameters": {
      "type": "object",
      "additionalProperties": false,
      "required": ["reply", "recommendation_status", "primary_product_id", "alternative_product_ids", "evidence_fields"],
      "properties": {
        "reply": {"type": "string", "minLength": 1, "maxLength": 320},
        "recommendation_status": {"type": "string", "enum": ["none", "proposed"]},
        "primary_product_id": {"anyOf": [{"type": "string", "minLength": 1}, {"type": "null"}]},
        "alternative_product_ids": {"type": "array", "items": {"type": "string"}, "maxItems": 2, "uniqueItems": true},
        "evidence_fields": {"type": "array", "items": {"type": "string"}, "maxItems": 12, "uniqueItems": true}
      }
    }
  }
}
```

**校验附加规则：**

- `recommendation_status=none` 时，`primary_product_id=null`，备选与证据字段为空数组；
- `recommendation_status=proposed` 时，首选与备选均须属于当前品类、当前商品库版本，且不得重复；
- `evidence_fields` 只能使用当前商品 schema 中的允许字段名；
- 结构、商品 ID 或证据字段任一校验失败时，整轮 AI 回复视为失败，不展示、不计回合，并记录失败原因。

#### 4.3.3 固定请求构造：`shopping-request-v1.0`

消息顺序严格为：系统 Prompt → 需求上下文 → 已保存的完整对话历史 → 当前用户消息。

需求上下文只包含 `catalog_version`、已选品类、购物需求和该品类的商品记录。商品按 `product_id` 升序，字段按固定 schema 顺序序列化。每次调用必须记录模型、参数、Prompt、工具 schema、商品库版本、尝试序号、提供商请求 ID 与校验结果。

### 4.4 决定、采纳与问卷

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| FR-15 | 决定页支持：选择一款商品、保留两款候选、暂不购买、无法决定。 | 原始提交只允许一次，保存 `decision_status` 与原始商品 ID。 |
| FR-16 | 系统保存 `recommendation_exposed`，仅当提交决定前实际展示过服务端校验的推荐时为真。 | 没有有效推荐卡时不得标记为已暴露。 |
| FR-17 | 系统按 `adoption-rule-v1.0` 派生采纳结果，不覆盖原始决定。 | 派生结果可基于原始决定和最后一次展示推荐重算。 |
| FR-18 | 问卷支持逐题自动暂存、断点恢复、必答校验和正式锁定。 | 正式提交后不可修改；缺题不得完成任务。 |
| FR-19 | 当需求、6 个有效回合、决定、完整问卷与版本字段均存在时，生成唯一 12 位完成码。 | 并发重复提交不生成多个完成码。 |

#### 4.4.1 `adoption-rule-v1.0`

| 条件 | `adoption_level` | `adoption_binary` |
| --- | --- | --- |
| 无推荐暴露 | `NULL` | `NULL` |
| 选择首选商品 | `full_adoption` | `1` |
| 选择备选商品；或保留两款且至少一款在推荐集合 | `partial_adoption` | `1` |
| 选择均不在推荐集合；或已看有效推荐后暂不购买 | `non_adoption` | `0` |
| 无法决定 | `no_decision` | `NULL` |

二分类分母仅包含 `recommendation_exposed=true` 且 `decision_status≠无法决定` 的任务。

#### 4.4.2 `survey-empathy-v1.0`

共同导语：**“请根据刚才的购物咨询，评价你对以下说法的同意程度：”**

所有题目均为 1—7 分：1＝完全不同意，7＝完全同意。

| 题号 | 维度 | 题目 |
| --- | --- | --- |
| C1 | 感知认知理解 | 这个 AI 准确理解了我的购物需求。 |
| C2 | 感知认知理解 | 这个 AI 把握了我在选择商品时真正关心的问题。 |
| C3 | 感知认知理解 | 这个 AI 理解了我的使用情境、偏好和限制条件。 |
| E1 | 感知情绪回应 | 这个 AI 察觉到了我在购物决策中的犹豫、担心或其他感受。 |
| E2 | 感知情绪回应 | 这个 AI 对我的顾虑作出了恰当回应。 |
| E3 | 感知情绪回应 | 这个 AI 的回答让我感到自己的感受得到了理解和尊重。 |
| A1 | 感知行动支持 | 这个 AI 根据我的具体情况提供了有针对性的建议。 |
| A2 | 感知行动支持 | 这个 AI 帮助我明确了下一步应该怎样选择。 |
| A3 | 感知行动支持 | 这个 AI 的回答降低了我的选择困难。 |

维度得分是本维三题的算术平均值；原始题项和聚合分数均须导出。

### 4.5 研究者后台与导出

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| FR-20 | 后台支持按时间、完成状态、品类、研究码核验状态和对话轮数筛选任务。 | 相同筛选下，列表数量与对应导出数量一致。 |
| FR-21 | 后台任务详情按时间线回放需求、消息、商品行为、推荐、决定、问卷和异常。 | 每条记录可显示稳定 ID、版本与服务端时间。 |
| FR-22 | 后台生成标准化数据导出，并记录导出人、时间、筛选条件、schema 版本和文件行数。 | 导出具备审计记录和 `export_manifest.json`。 |

## 5. 数据设计

### 5.1 关联规则

所有事实记录使用稳定 ID 关联：`participant_id`、`task_id`、`message_id`、`product_id`。记录级实体另有 `event_id`、`recommendation_id`、`survey_submission_id` 和 `question_id`。不允许将完整对话、行为和问卷混存为无法查询的大字段。

### 5.2 最小实体

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| participants | `participant_id`、`study_token_hmac`、`consent_version`、`consented_at`、`status` | 不存储原始研究码 |
| tasks | `task_id`、`participant_id`、`category`、需求字段、`status`、开始/完成时间 | 一位参与者对应一次任务 |
| messages | `message_id`、`task_id`、`turn_number`、`role`、正文、时间、幂等键、AI 请求信息 | 人类和 AI 消息逐条保存 |
| products | `product_id`、品类、商品事实字段、`catalog_version`、`is_active` | 固定商品库 |
| product_events | `event_id`、`task_id`、`product_id`、`event_type`、时间、元数据 | 商品交互事件 |
| recommendations | `recommendation_id`、`task_id`、`message_id`、首选/备选 ID、证据字段、展示状态 | 仅保存校验通过的结构化推荐 |
| decisions | `decision_id`、`task_id`、原始决定、候选、推荐暴露、采纳字段、规则版本 | 原始字段与派生字段并存 |
| survey_responses | `survey_submission_id`、`task_id`、题号、答案、问卷版本、草稿/正式状态 | 逐题可恢复 |
| experiment_versions | 模型、Prompt、工具、商品库、问卷、采纳规则、政策、发布版本 | 支持样本条件核查 |
| export_audits | `export_id`、研究者、筛选条件、时间、schema、行数 | 导出审计 |

### 5.3 导出格式

必须生成：`participants.csv`、`tasks.csv`、`messages.jsonl`、`product_events.jsonl`、`recommendations.jsonl`、`decisions.csv`、`survey_responses.csv`、`credamo_verifications.csv`、`experiment_versions.csv`、`analysis_sample.csv`、`data_dictionary.md` 与 `export_manifest.json`。

`analysis_sample.csv` 一行一个完成任务；其行数必须等于同一筛选条件下状态为 `COMPLETED` 的任务数。

## 6. 服务端接口

| 方法与路径 | 用途 | 核心校验 |
| --- | --- | --- |
| `POST /api/sessions` | 校验同意版本和研究码，创建/恢复会话 | 研究码规范化、HMAC、单任务约束 |
| `POST /api/tasks/:id/messages` | 保存用户消息并请求 AI | 权限、状态、幂等键、回合锁、工具结构校验 |
| `POST /api/tasks/:id/product-events` | 写入商品行为 | 权限、商品属于当前品类、事件幂等 |
| `POST /api/tasks/:id/decision` | 保存原始决定并派生采纳字段 | 有效回合、状态、商品 ID、单次正式提交 |
| `PUT /api/tasks/:id/survey-draft` | 自动暂存问卷 | 权限、题号、量表范围、幂等 |
| `POST /api/tasks/:id/survey-submit` | 校验并锁定问卷 | 9 题完整、状态、单次提交 |
| `POST /api/admin/credamo-verifications` | 导入 Credamo 核验表 | 后台权限、文件 schema、HMAC 匹配 |
| `POST /api/admin/exports` | 创建数据导出 | 后台权限、筛选审计、schema 版本 |

接口返回不得泄露 AI 密钥、原始研究码、其他参与者数据、内部提示词或供应商完整错误信息。

## 7. 非功能需求

### 7.1 安全与隐私

- AI API Key、数据库凭据、管理员密码和 HMAC 密钥仅存于服务端环境变量；
- 参与者端与后台必须实施访问控制，后台需登录；
- 研究码仅以规范化后 HMAC 形式落库；
- 管理操作和数据导出必须形成审计记录；
- 外部 AI 请求不包含研究码、完成码、IP、人口信息或身份字段；
- 必须配置 HTTPS、输入长度限制、基础脚本过滤、参数化数据库访问与重复提交防护。

### 7.2 可恢复性与一致性

- 消息、商品事件、问卷草稿和决定写入应支持幂等；
- 用户消息必须在 AI 调用前提交成功；
- AI 调用失败后不得生成“成功 AI 回复”或增加有效回合；
- 已保存数据在页面刷新、网络短断和重进后可恢复；
- 完成码以服务端事务生成，确保同一任务只能产生一个。

### 7.3 可用性与设备

- 桌面端以聊天为主、商品为辅助；
- 在最小 390px 宽度下，品类、需求、聊天、决定和问卷均可完整操作；
- 输入框、发送、结束购物和问卷提交操作不能被遮挡或发生横向滚动；
- 每次 AI 调用应展示进行中、成功或失败状态。

## 8. 异常处理

| 场景 | 服务端行为 | 前台行为 |
| --- | --- | --- |
| AI 超时/错误 | 记录请求和失败原因；同参数最多自动重试一次；不计回合 | 显示简明失败提示和手动重试入口 |
| 重复点击发送 | 依据幂等键返回原结果或处理中状态 | 禁用重复发送并显示发送状态 |
| 页面刷新/中途退出 | 保留任务状态和全部已保存记录 | 同研究码恢复到上次可继续步骤 |
| 无效/重复研究码 | 不创建或复制任务，记录异常 | 显示不能开始或已完成提示 |
| 商品 ID 无效 | 拒绝写入事件、推荐或决定 | 显示通用错误，不显示内部细节 |
| 问卷漏答 | 不锁定、不完成 | 定位提示未回答题目 |
| 数据写入失败 | 事务回滚，保留错误审计 | 提醒稍后重试，不展示敏感技术信息 |

## 9. 测试与验收

### 9.1 自动化测试

- 单元测试：任务状态转移、有效回合、结构化 AI 校验、采纳派生、完成码幂等；
- 集成测试：消息先保存后调用 AI、重试、恢复、问卷锁定、导出数据一致性；
- 端到端测试：桌面端与 390px 手机端从进入到完成的完整流程；
- 合约测试：AI 工具 JSON Schema、商品库字段、导出 schema。

### 9.2 发布前必测场景

| 场景 | 必须验证的结果 |
| --- | --- |
| 刷新与后退 | 已填写需求、消息、商品行为和问卷草稿均能恢复。 |
| 同一研究码重复打开 | 不产生第二个任务或第二个完成码。 |
| 并发发送与重复提交 | 不产生重复消息、决定、问卷或完成码。 |
| AI 调用异常 | 成功重试后只保存一条 AI 回复；重试失败后不增加回合。 |
| 无推荐任务 | `recommendation_exposed=false`，采纳字段为 `NULL`。 |
| 四种决定 | 原始决定、推荐集合与派生采纳规则正确。 |
| 真实 Credamo 闭环 | 研究码、完成码、错码、重复码、空格和大小写规范化均通过测试。 |
| 导出回放 | 一次任务可按时间还原；汇总表完成行数与后台完成任务数一致。 |
